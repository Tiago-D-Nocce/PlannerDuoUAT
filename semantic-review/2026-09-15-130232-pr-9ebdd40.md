# Session-only Firebase bootstrap turns startup delays into lockouts

Commit `9ebdd40` adds a Firebase Auth supervisor, sanitized error reporting, and deterministic login routing. Credential enumeration and raw-error leakage are avoided, but persistence latency, blocked storage, and unrelated startup errors now become terminal failures. A browser with working internet can therefore show a permanent connection error or never start the Auth observer. The uncancellable three-second persistence race is the **likely** live trigger; the global watchdog is the other plausible path, but it discards the event detail needed to distinguish them in production.

Watch for: **confirmed** — `setPersistence(SESSION)` finishing after three seconds is ignored although the Firebase operation continues, leaving login/app startup failed; **confirmed** — any global error or unhandled rejection during bootstrap permanently poisons readiness and is rendered as an internet problem.

**Verdict**: NEEDS_CHANGES

## High-level view

`firebase.auth()` is created on each page, then `setPersistence(SESSION)` is started and wrapped in an independent three-second timer. **confirmed:** the timer cannot cancel Firebase, but its rejection is terminal: `auth.html` reuses the rejected promise for login, registration, Google login, account switching, and redirect recovery, while `app.js` never registers `onAuthStateChanged`.

The app repeats the persistence mutation after the auth page already selected `SESSION` before sign-in. **confirmed:** this second gate adds another failure point before Firebase can report either the restored user or the signed-out state, leaving the loader as the only usable app surface.

The supervisor starts a ten-second wall-clock timer before the Firebase CDN scripts and listens to every global `error` and `unhandledrejection`. **confirmed:** all categories produce the same connectivity message and an irreversible `erro` state; on the app page, even later Auth/Firestore success remains hidden.

The auth page declares bootstrap ready when persistence succeeds, before invoking `getRedirectResult`. **confirmed:** redirect recovery has no watchdog, and the shared catch reports a persistence rejection as `google-redirect` even when no Google login was attempted.

The smallest secure design is one Auth owner that selects `SESSION` before sign-in, does not mutate persistence again on the app path, and falls back to `NONE` only for an actual storage-capability rejection. Because `NONE` cannot survive the current `auth.html` → `app.html` reload, that fallback must retain the same Auth instance in a single-document shell and use popup for federated login; `LOCAL` or token handoff through URLs/storage would weaken the stated session boundary.

## `auth.html` persistence and redirect ordering

The supervisor enters `pendente`, attaches global listeners, and starts its ten-second timer before Firebase loads. After `firebase.auth()` returns the page singleton, JavaScript evaluates `auth.setPersistence(SESSION)` before passing its already-running promise to `limitarOperacaoAuth`; the helper then adds its own three-second timer.

```text
bootstrap.iniciar() ── global listeners + 10 s timer
        │
        ├─ Firebase scripts / initializeApp / firebase.auth()
        │
        └─ setPersistence(SESSION) starts
                 └─ limiter attaches + 3 s timer
                        ├─ success ≤3 s → bootstrap.concluir()
                        │                  └─ getRedirectResult()
                        └─ reject/timeout → bootstrap.falhar()
                                           └─ persistenciaPronta rejects
                                              └─ redirect-chain catch
```

On success, the first `.then` marks bootstrap ready and fulfills `persistenciaPronta`; the next reaction starts `getRedirectResult`. Login, registration, account switching, and Google login await the same promise. Password reset bypasses it.

On failure, the first handler records the persistence error, makes bootstrap terminal, updates the panel, and rethrows. The final redirect `.catch` is attached during the same script task, so **confirmed:** the persistence rejection is handled and normally does not fire `unhandledrejection`. It is still toasted as `google-redirect`, and every later login/registration/Google attempt receives the already-rejected promise without calling Firebase.

**confirmed, P0:** `limitarOperacaoAuth` settles once and does not cancel `setPersistence`. Completion at 3.001 seconds cannot reopen `persistenciaPronta`; an actual `auth/web-storage-unsupported` or `auth/unsupported-persistence-type` rejection is equally terminal. Slow initialization, private mode, or restrictive storage policy can therefore create a reload loop despite network access.

## `app.js` observer is behind a second terminal gate

The app starts another persistence operation during script evaluation. Its rejection handler converts failure into fulfilled `false`, so **confirmed:** `persistenciaAuth` itself does not emit an unhandled rejection. At `DOMContentLoaded`, `true` registers `onAuthStateChanged`; `false` calls `_falharBootstrap('autenticacao')` and never registers it.

The observer’s initial callback arrives after Firebase restores Auth state. Signed-out state concludes bootstrap and redirects; signed-in state allows up to six seconds for `casalId`, mounts the shell, checks the supervisor state, reveals the shell, and concludes bootstrap.

**confirmed, P0:** persistence failure prevents discovery of both a valid session and signed-out state. **confirmed, P1:** the ten-second budget includes CDN loading, Firebase initialization, persistence, the initial callback, and the six-second Firestore lookup; if it expires first, `_entrarNoApp` later sees `erro` and deliberately keeps an otherwise initialized app hidden.

Persistence should be selected before sign-in by the auth owner. The app path should subscribe immediately to `onAuthStateChanged` and hydrate the secure session already created, rather than call `setPersistence` again.

## Global failures become irreversible connectivity failures

`aoRejeicaoGlobal` ignores the rejection reason and makes every unhandled promise fatal. `aoErroGlobal` does the same for runtime errors, distinguishing only `script`/`link` targets. `mostrarFalha` uses “Verifique sua conexão” for timeout, resource, SDK, authentication, Firestore, and initialization categories.

**confirmed, P1:** a startup crossing ten seconds, a synchronous storage exception, blocked CDN/CSP resource, unrelated rejection, or ordinary initialization bug can all produce the reported internet screen. `falhar` then refuses every later `concluir`; on the app route this remains an availability failure until reload.

Explicit failure of a critical Firebase script may remain fatal. Global runtime/rejection events should be sanitized telemetry, while only owned startup promises control readiness. A watchdog may expose status and retry, but late success must be able to clear it.

## Google redirect runs after readiness is declared

**confirmed, P1:** `PlannerBootstrap.concluir()` runs before `getRedirectResult`. A redirect result that never settles has no persistent recovery path, while rejection gets only a transient toast; the same catch also receives persistence failures and labels them as redirect failures.

Redirect recovery should be inside the readiness promise: select persistence, resolve the pending redirect, establish initial user state, then mark ready. A `null` result leaves controls enabled, cancellation stays silent, and storage/origin/network failures remain distinct. In `NONE` mode, use popup and retain the same document because redirect and the app-page navigation cannot preserve in-memory Auth.

## One Auth owner with `SESSION` → `NONE` fallback

A coordinator should initialize Firebase once, select `SESSION`, process redirect state, subscribe once to Auth state, and expose a typed readiness result. On an actual storage-capability rejection it may select `NONE`, which is stricter than `SESSION`, but must keep the UI and app shell on the same Auth instance. It must not start a fallback after a synthetic timeout because the original uncancelled persistence operation can still settle later.

Do not fall back to `LOCAL`, raw ID tokens, query parameters, or ad-hoc token storage. Keep the new sanitized diagnostics and credential-enumeration protection. If a single-document fallback is not acceptable, storage denial must be reported precisely as unsupported rather than as an internet failure; the current multi-page design cannot both use `NONE` and preserve login across navigation.

## Browser-level deployment gate

The focused Vitest suites pass 34 tests, but **confirmed, P1:** they assert source strings and the intended terminal behavior rather than run the browser orchestration with Firebase. One test requires login not to start after the synthetic timeout, and another requires late bootstrap success to be ignored, preserving the failure contract.

Required promise-order tests need deferred Firebase promises and fake timers for late persistence success, actual storage rejection and `NONE` fallback, exactly-once observer registration, recovery after a watchdog notice, separation of persistence from redirect errors, and an unrelated `Promise.reject` that does not poison readiness. Critical Firebase script failure must still expose persistent retry.

Required auth-flow tests must cover redirect user/null/cancellation/storage/origin/network outcomes and a pending redirect while controls remain recoverable. Delayed signed-in and signed-out observer states must recover beyond ten seconds. Session semantics must be verified across reload, tab close/reopen, duplicate tabs, logout, and account switching.

Before deployment, run email/password, registration, reset, Google login, cancellation, refresh, back navigation, and close/reopen on current Chrome, Edge, Firefox, desktop/iOS Safari, and Android Chrome. Include private modes, blocked third-party cookies, denied web storage, slow CPU/network, authorized-domain errors, popup/redirect restrictions, and CDN/CSP blocking. Storage denial must yield either a working same-document `NONE` login or a precise unsupported-browser message, never an internet diagnosis or reload loop.
